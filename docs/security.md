# Security

## Authentication model

Meetingtime has no user accounts and no password directory. Authentication is per-meeting and per-participant: when a participant joins (or creates) a meeting, the server issues them a random 24-byte base64url token generated by `node:crypto.randomBytes`. The token is stored only in the participant's browser (`localStorage`, key `mt:session:<meetingId>`) and is required for every host-sensitive action. The server checks the token through the `requireHost(socket)` guard before mutating any meeting state. Tokens never leave the server's `Meeting.tokens` map: they stay out of `meeting:state` broadcasts.

Meeting IDs (`MRX7-92AB` shape) are generated with `node:crypto.randomInt` over a 31-character alphabet, in two four-character blocks. The keyspace is roughly 8.5 × 10^11, which combined with the optional password and (in production) `CORS_ORIGIN` makes blind guessing impractical. The previous implementation used `Math.random`, which is predictable across calls once an attacker observes a few IDs; that has been fixed.

## Per-meeting password

The host can set an optional password at creation time. The plaintext password is stored privately on the `Meeting` instance and is never broadcast; only `state.hasPassword` (a boolean) leaves the server. Verification goes through `Meeting.verifyPassword(supplied)` using a constant-time-ish comparison (length check first, then per-character XOR) so the timing surface is minimised. The password is only enforced on the identity flow of `meeting:join`; reconnections via a previously issued token skip the check because they are already authenticated. Empty or whitespace-only strings are normalised to "no password", and the value is capped at 128 characters so a malicious payload cannot fill memory.

On the client, the password is persisted in **sessionStorage** (tab-scoped, never written to disk) so the share dialog can be re-opened from the meeting page without re-prompting. It is wiped as soon as the meeting transitions to `ended` and again when the host explicitly leaves via the ended-banner "Home" button. The direct join link rendered in the share dialog deliberately does not include the password: URLs leak via browser history, the Referer header and screen sharing.

## CORS and origin restriction

`CORS_ORIGIN` defaults to `*` for ease of local development. In production, set it explicitly to your own origin (typically `https://meetingtime.example.com`) so Socket.IO rejects cross-origin connections. The Yjs WebSocket upgrade applies the same origin check: any browser opening the WS from a different origin is closed with `HTTP 403 Forbidden` before the protocol handshake completes. This blocks Cross-Site WebSocket Hijacking attempts even on hosts where the token might somehow leak. All deployment variants under `deploy/` set `CORS_ORIGIN` automatically based on `MEETINGTIME_DOMAIN`.

## Security headers

Every HTTP response carries a defensive header set, defined in `server/src/plugins/securityHeaders.ts`:

- `Content-Security-Policy` restricts scripts to `'self'` (no inline, no eval), styles to `'self' 'unsafe-inline'` (Shiki emits inline `style="…"` attributes that CSP2 lumps under style-src), images to `'self' data: https:`, fonts to `'self'`, connections to `'self' ws: wss:`, and forbids framing entirely (`frame-ancestors 'none'`), objects (`object-src 'none'`) and form submissions to anywhere but the same origin.
- `X-Content-Type-Options: nosniff` blocks MIME-sniffing-based attacks.
- `Referrer-Policy: no-referrer` prevents the URL (which contains the meeting ID) from leaking to third parties.
- `X-Frame-Options: DENY` is a belt-and-braces version of `frame-ancestors 'none'` for older browsers.
- `Permissions-Policy: camera=(), microphone=(), geolocation=()` denies access to powerful browser APIs the app does not use.
- `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Resource-Policy: same-origin` isolate the document's browsing context from other origins.
- `Strict-Transport-Security: max-age=15552000; includeSubDomains` is emitted **only** when the request reached the app over HTTPS (either directly or through a trusted proxy that set `X-Forwarded-Proto: https`). Plain-HTTP LAN deployments are never downgraded.

## Reverse-proxy trust

Setting `TRUST_PROXY=1` makes Express honour the `X-Forwarded-*` headers your reverse proxy sets, so the source IP logged by Pino is the real client, not the proxy itself, and `Strict-Transport-Security` is emitted on proxied HTTPS requests. All `deploy/` variants enable this safely. Do **not** set it when the app is exposed directly to the public internet without a proxy, and do **not** set it behind a proxy that forwards inbound `X-Forwarded-*` headers untouched. A remote caller would then be able to spoof their IP by sending the header themselves, so any future IP-based rate limit, abuse heuristic or forensic log would be defeated. The deployment variants under `deploy/` (Caddy, nginx, Traefik) all strip or overwrite the inbound headers before forwarding, which is why enabling `TRUST_PROXY=1` there is safe.

## Input validation and resource caps

Every `meeting:create`, `meeting:join` and `participant:add` payload is run through `sanitizeIdentity()` before reaching the model: each field is coerced to a string, trimmed, and clamped to sixty characters. The `Meeting` class also defensively re-clamps in `createParticipant()` so any future caller that forgets the handler-level guard still hits the same limits. Reorder events validate the `direction` enum (`"up" | "down"`) up front. Meetings enforce hard caps on participants (200), topics per agenda (100), topic label length (200 characters), password length (128 characters), per-speaker timebox (one hour) and planned meeting duration (twenty-four hours). Any attempt to exceed those caps returns a stable error code (`participant_cap_reached`, `topic_cap_reached`, `empty_label`, `invalid_direction`) instead of growing memory.

Socket.IO is configured with `maxHttpBufferSize: 100_000` so a single oversized event cannot bloat memory; the Yjs WebSocket bridge enforces `maxPayload: 64 KiB` for the same reason. Every socket listener is registered through a guard that catches exceptions from malformed frames (missing payload, non-function ack) and acknowledges with `invalid_payload`; Socket.IO does not catch listener exceptions itself, and the process-level crash handler would otherwise turn one malformed frame into a full restart. Socket handlers no longer echo raw exception messages back to the client: unexpected throws are logged through Pino (without identifying data) and acknowledged with a generic `internal_error` code (whitelisted business codes like `participant_cap_reached` still pass through), so dependency internals, file paths and library traces cannot leak to a remote caller.

## Live authorization

`socket.ctx.participant` is a reference captured when the socket attaches. Without a freshness check, a participant removed from the meeting (or demoted from host) would keep passing the guards until they disconnected on their own. `requireHost` and `ctxOf` re-resolve the participant from the live meeting state on **every** call, so a removed-or-demoted participant is denied immediately. On top of that, `participant:remove` proactively force-disconnects every socket still authenticated as that participant.

## Rate limiting

Four complementary budgets, all in-memory:

- **Per-IP connection budget** (`server/src/plugins/rateLimit.ts`): three hundred requests per minute per IP. The same counter is consulted from three places so the limit cannot be bypassed by switching transports: the Express middleware (HTTP requests including SPA fallback and the Socket.IO long-poll fallback), the Socket.IO handshake middleware (WebSocket transport), and the Yjs WebSocket upgrade. The budget is sized for shared egress: a cold SPA load is 10-30 requests, and several colleagues behind one office NAT share a single IP. `/healthz` is served before the gate so container health probes are never throttled and never consume the budget.
- **Per-Socket.IO-socket event budget**: eighty events per ten seconds. Every Socket.IO event goes through `socket.use` and is dropped past the threshold; the socket is then disconnected. Without this, an authenticated peer could spam any cheap event (for example `speaker:grant`) at line rate, and since every handler triggers `broadcastState` to every participant, each malicious emit would amplify into `N × (full meeting JSON)` broadcast bytes.
- **Per-Yjs-WebSocket message budget**: two hundred incoming messages per ten seconds per connection. Same amplification reasoning as above (a flooded awareness or sync update is re-broadcast to every other peer in the doc). Past the budget the connection is terminated.
- **Idle-join timeout**: a Socket.IO connection that does not authenticate (via `meeting:create` or `meeting:join`) within ten minutes is force-disconnected (long enough for a host to fill the create form). Without this, an attacker could open the per-IP connection cap and sit on each socket indefinitely, holding the budget while doing nothing.

All four stores are in-memory only and sweep stale entries on the minute. They are meant to deter spray and amplification attacks, not to be airtight against an attacker rotating IPs or coordinating many clients. Combine with a reverse proxy or upstream WAF for stricter posture.

## Phase-aware authorization

Beyond `requireHost`, every host mutation (`participant:add`, `participant:remove`, `participant:reorder`, `host:promote`, `host:demote`, `meeting:setTimebox`, `meeting:setTimeboxEnabled`, `topic:add`, `topic:remove`, `topic:reorder`, `topic:setCurrent`) explicitly rejects with `meeting_ended` when the meeting is already terminated. The UI already gates the corresponding buttons, but the server enforces independently so a hand-crafted client cannot mutate a meeting that has been ended (and is about to be wiped from memory by `POST_END_GC_MS`).

## Notes editor: Yjs awareness colour

CodeMirror remote-cursor decorations interpolate the participant's awareness `color` field into an inline `style="…"` attribute. The local client validates its colour against `^#(?:[0-9a-fA-F]{3}|[0-9a-fA-F]{6})$` before pushing it into awareness, so accidental injection from our own code is impossible. A determined participant patching their own browser client could still bypass that local guard and push raw CSS into awareness, where it would be applied verbatim by other participants' editors. The blast radius is limited to **CSS injection inside the notes editor of in-meeting peers** (the existing CSP prevents script execution and limits image origins). We accept this residual risk because the mitigation would require either forking `y-codemirror.next` to sanitise incoming awareness states or running the WebSocket bridge through a Yjs awareness parser; neither is justified for the in-meeting threat model where peers are already trusted enough to read and edit notes.

## Graceful shutdown and crash recovery

The server listens for `SIGTERM` (container stop) and `SIGINT` (Ctrl-C). On either signal it stops accepting new HTTP and WebSocket connections, force-disconnects every Socket.IO client so they see the standard "disconnected" banner instead of hanging, closes the Yjs WebSocket bridge with a `1001 server_shutting_down` close code, then exits. A hard 10 s deadline prevents a stuck connection from blocking the container restart. Meeting state is in-memory and lost on restart by design; the client's stored session token causes a clean rejoin attempt once the new process is up. The Dockerfile drops to the unprivileged `node` user (uid 1000) so a code execution vulnerability in any dependency cannot trivially compromise the container's filesystem.

The process installs `uncaughtException` and `unhandledRejection` handlers that log the error with stack trace and trigger the same graceful shutdown. We deliberately do not attempt to recover and keep serving: an unknown post-crash state risks silent data corruption, and the orchestrator (Docker/systemd/Kubernetes) is the right place to bring the process back on a clean slate.

## Liveness and dead-socket cleanup

The Yjs bridge pings every connected WebSocket every thirty seconds and terminates the connection if two consecutive pings go unanswered. This reclaims slots held by laptops closed mid-meeting, NAT-dropped connections and similar dead-but-half-open sockets that the OS alone would only reap minutes (or hours) later.

## Memory hygiene

Meeting state never touches disk. The server holds it in `MeetingStore`, an in-memory `Map<id, { meeting, ydoc, lastActivity }>`. Two GC paths remove it:

- An idle sweep runs every minute and deletes any meeting that has no connected participant and whose `lastActivity` is older than `HOST_TIMEOUT_MS` (default thirty minutes).
- The `meeting:end` handler schedules a one-shot deletion `POST_END_GC_MS` later (default five minutes). The delay gives the client enough time to export the Markdown notes from the still-live Yjs document; after that, the password, tokens, participants, topics and Y.Doc are all wiped.

When a meeting is deleted, the bridge-side state on the Yjs server (`docStates` map plus awareness instance) is released too, so the bridge cannot accumulate dead doc references across meeting churn. No file or database persists anything across container restarts. A redeploy wipes every meeting.

## Notes and Yjs

The Yjs WebSocket bridge (`server/src/yjs/ywsBridge.ts`) silently drops `update` messages coming from non-host sockets, so guests can read the notes in real time but cannot edit them. The room URL embeds the participant token (`/yjs/<meetingId>?token=…`) so the bridge can identify the participant on connect. The Origin header is checked at upgrade time against `CORS_ORIGIN` and rejected before the protocol handshake if it does not match.

## Output sanitisation

The Markdown preview is sanitised by DOMPurify before insertion (`ADD_ATTR: ["style"]` preserves the inline `--shiki-*` CSS variables that Shiki emits for syntax-highlighted code blocks). No other code path uses `innerHTML` for arbitrary content. Lucide icons are injected as inline SVG through a typed helper that only accepts pre-bundled icon names. The keyboard-help dialog interpolates shortcut labels into a `<kbd>` element with `innerHTML`, but the labels are compile-time constants in `KeyboardHelpDialog.ts`, not user input.

## Logging

Pino is configured to log at the `info` level by default. No notes content, no identity (first name, last name, role), no token and no password ever appears in the logs. Handler exceptions are logged with the error message but without the source payload. Increase the level to `debug` only on a host you trust.

## No external network calls at runtime

No CDN, no analytics, no font fetching. Fonts are self-hosted via `@fontsource-variable/inter` and `@fontsource-variable/jetbrains-mono`. Shiki grammars and themes ship bundled by Vite. The app runs unmodified on an air-gapped host.

## Session-switch hygiene

A client that re-issues `meeting:join` with a different meeting ID on the same socket has its previous attachment cleanly torn down before the new one: the previous meeting room is left (so the socket stops receiving its state broadcasts) and the previous participant is marked disconnected, unless another device of the same participant is still connected there. Without this, a single socket could subscribe to multiple meetings' state streams in parallel and the old meeting would forever show the participant as connected.

## What is **not** implemented

- **No cluster-safe rate limiter.** Every budget lives in the single Node process's memory. Behind a load balancer with multiple workers an attacker could get the limit per worker. Pin to a single instance, sticky-session your proxy, or replace with Redis if you scale out.
- **`TRUST_PROXY=1` trusts exactly one hop.** Express's `trust proxy 1` reads `X-Forwarded-For` from the last hop only. If you chain two reverse proxies in front of Meetingtime, only the closest one is trusted; the further hops can be spoofed. Bump to `trust proxy 2` (or higher) only when every intermediate hop strips inbound `X-Forwarded-*` from client requests.
- **A single `CORS_ORIGIN` is supported.** Multi-origin setups (staging + prod on the same server) must run one container per origin.
- **Tokens never expire.** Once issued, a token is valid until the meeting is deleted from server memory (idle GC after `HOST_TIMEOUT_MS` or `POST_END_GC_MS` after `meeting:end`). A participant who leaks their token to a third party gives them indefinite access to that meeting.
- **Identity-flow joins merge by name.** A password-flow join whose first name, last name and role match an existing participant reuses that participant (including their host status and token) instead of creating a duplicate, so one person can join from two devices as a single identity. The meeting password is the only gate, and note that every participant already knows it and sees everyone's name and role in the list: any guest who types the host's exact identity joins **as that host**, gaining host controls and notes write access. This is an accepted trade-off for the small, trusted meetings the app targets (the alternative would break the second-device flow); do not run meetings with untrusted strangers and a host whose identity they can read.
- **Notes document size is unbounded.** Yjs growth is proportional to edits; nothing caps the underlying `Y.Text`. A malicious host could write hundreds of megabytes of notes before the meeting ends. The per-meeting memory cap is therefore soft, not hard.
- **Tokens are stored in `localStorage`.** They survive XSS theft. The app deliberately has no `innerHTML` of untrusted content, so the XSS surface is the Markdown preview only, sanitised by DOMPurify and locked down by the CSP above. If a future feature introduces a richer surface, move tokens to an HttpOnly cookie.
- **The Yjs token is passed as a URL query parameter.** Browsers do not send `Referer` on `ws://` upgrades, but server access logs (if you turn them on) would capture it. Pino is not configured to log the WS upgrade, so this is mitigated in the default setup.
