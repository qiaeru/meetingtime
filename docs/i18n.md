# Internationalisation

Meetingtime ships in French, English, Spanish, Italian and German. The locale is detected automatically on first visit from the browser's `navigator.language`, with English as the fallback (not French). The user's choice is then persisted in `localStorage` under the key `mt:locale` and is honoured on subsequent visits. The language picker sits in the header of every page.

## Canonical locale lists

Two canonical sources hold the list of supported locales:

- `client/src/i18n/index.ts` exports `SUPPORTED_LOCALES`, used by the picker and by the runtime `t()` helper.
- `server/src/lib/locales.ts` exports `SUPPORTED_LOCALES`, used by the manifest content-negotiation route and by anything else server-side that needs to pick a language.

Never hardcode `["fr", "en"]` (or any other locale tuple) anywhere else in the codebase. A literal sitting in a feature module silently freezes that feature to those two locales the next time the canonical list grows.

## Adding a language

1. Create `client/src/i18n/locales/<code>.json` by copying `en.json` and translating every value. Keys must match exactly (run `node -e "const f=Object.keys(require('./client/src/i18n/locales/<code>.json'));const e=Object.keys(require('./client/src/i18n/locales/en.json'));console.log(f.filter(k=>!e.includes(k)),e.filter(k=>!f.includes(k)))"` to verify both directions).
2. Extend the `Locale` union in `shared/src/models.ts` (for example `"fr" | "en" | "de"`).
3. Import the new dictionary in `client/src/i18n/index.ts` and add the entry to `SUPPORTED_LOCALES`. The new language appears automatically in the picker, sorted by native name.
4. Add the matching entry to `server/src/lib/locales.ts:SUPPORTED_LOCALES`.
5. Create `client/public/manifest.<code>.webmanifest` mirroring the structure of the existing manifests (translate `description`, keep `lang` aligned with the code).

## PWA manifest

The browser always requests `/manifest.webmanifest` (one file, locale-neutral URL). The server route handles content negotiation: it parses `Accept-Language`, picks the best match from `SUPPORTED_LOCALES`, and returns the matching `client/public/manifest.<locale>.webmanifest`. The Vite dev server proxies `/manifest.webmanifest` to the API so the same URL works in development.

## Writing rules

Keys follow a flat namespace convention: `domain.action` (for example `meeting.giveFloor` or `share.copyMessage`). Interpolations use `{name}` placeholders that `t("key", { name: "Alice" })` substitutes. When a key is missing in the active locale, `t()` falls back to French first, then to the raw key, so a missing translation is visible without crashing the page.

## Verification

Open the app, switch language from the picker on each page, and walk through every screen (home, create, join, meeting, dialogs, toasts). No displayed string should look like a raw key (for instance `meeting.giveFloor`). Then check that every locale stays in sync against the French source of truth:

```bash
node -e "const ls=['fr','en','es','it','de'];const d={};for(const l of ls)d[l]=require('./client/src/i18n/locales/'+l+'.json');const ref=Object.keys(d.fr);for(const l of ls){if(l==='fr')continue;const k=Object.keys(d[l]);const m=ref.filter(x=>!k.includes(x));const e=k.filter(x=>!ref.includes(x));if(m.length||e.length)console.log(l,'missing',m,'extra',e)}"
```
